## Task 1: Добавить локальный браузерный регрессионный контур

### Намерение
Зафиксировать симптом пользователя до изменения CSS/JS: контент есть в DOM, но может оказаться невидимым или перекрытым. Один тестовый запуск должен поднимать сам сайт и проверять рабочую страницу, а не копию фрагмента.

### Последовательность реализации
1. Создать приватный package.json с type=module и скриптами start, test и check:assets. Добавить @playwright/test как devDependency и создать package-lock.json. Не добавлять framework, сборщик, runtime-зависимость или backend.
2. Создать scripts/serve-site.mjs на Node.js core-модулях. Сервер слушает только 127.0.0.1:4173, обслуживает файлы из корня проекта, выставляет MIME-типы для html/js/css/png/jpg/svg/ttf и отклоняет путь, нормализованный за пределы корня.
3. Создать playwright.config.js с testDir=tests/e2e, baseURL=http://127.0.0.1:4173, Chromium и webServer command=npm run start. Для webServer ожидать HTTP 200 от корня; повторно использовать уже запущенный локальный сервер только вне CI. Использовать поддерживаемую конфигурацию webServer из официальной документации Playwright: https://playwright.dev/docs/test-webserver.
4. Создать tests/e2e/visibility.spec.js. Каждый тест загружает настоящую /index.html. Сценарий отказа прерывает только удалённые script-запросы, но оставляет локальную страницу и stylesheet; это отделяет отказ GSAP/ScrollTrigger от отказа базовой разметки и стилей.
5. Проверить при ширинах 390×844, 768×1024 и 1440×900 заголовок #hero h1, год 2026 и секции #prizes, #tracks, #stages, #portfolio, #documents, #history, #faq и #cta. Для каждой секции проверять непустой текст заголовка, bounding box больше нуля, visibility=visible и итоговую opacity больше 0.95 после перехода/ожидания fallback.
6. Для начального hero при scrollY=0 проверить --hero-prize-progress около 0, что центр текста заголовка попадает в #hero .hero-s_logo после hit-test и что текст/разбитые .split-char не имеют opacity:0. Приложить диагностический вывод viewport, progress и computed styles к падению теста.
7. Добавить отдельный сценарий prefers-reduced-motion=reduce: все заголовки и основной текст должны оставаться видимыми, а движение не должно быть обязательным условием теста.
8. Настроить Playwright сохранять screenshots, trace и HTML report только в test-results/ и playwright-report/. Не сохранять артефакты проверки в корень проекта.

### Интерфейсы и контракты
- npm test запускает Playwright в Chromium; npm run start запускает только локальную раздачу файлов; никакой генерации/переписывания index.html сервером нет.
- Контракт страницы проверяется по существующим section ID и заголовкам: #hero → h1 «Лучшая учебная группа» и 2026; #prizes → «Главный приз»; #tracks → «Треки»; #stages → «Этапы»; #portfolio → «Портфолио»; #documents → «Документы»; #history → «История»; #faq → «FAQ и контакты»; #cta → «Регистрация».
- Сценарий без удалённых скриптов не требует внешней сети. Ошибки загрузки намеренно отменённых CDN-скриптов записываются как ожидаемое условие, но pageerror из локального app.js считается ошибкой.
- Мобильный/desktop список размеров фиксирован в тесте, чтобы проверять обе ветви media queries и промежуточный диапазон 768 px.

### Ошибки и логирование
- Невозможность открыть порт 4173 должна завершать запуск Playwright с явной ошибкой webServer, а не переключать тесты на чужой сайт.
- В режиме verbose прикладывать к падению ошибки страницы, текущий URL, viewport, section ID, computed opacity/visibility и значение hero progress. Не выводить данные формы и не включать повторяющиеся сообщения на каждый scroll.

### Тесты
- Добавить тесты в tests/e2e/visibility.spec.js; до Tasks 3–4 ожидается, что assertions на текущую визуальную регрессию могут падать. Красный исход подтверждает чувствительность тестов и не считается завершённой проверкой фазы.
- Команды: `npm install` затем `npx playwright install chromium` и `npm test`. После реализации UI исправлений Task 7 должен быть зелёным.

### Критерии приёмки
- Команда `npm test -- --list` перечисляет тесты, а webServer поднимает страницу без дополнительного внешнего dev-сервера.
- Тесты ссылаются на реальные ID в index.html и покрывают все девять основных секций.
- Тест результата намеренно блокирует только внешние scripts; локальные изображения/стили остаются доступны.
- Ни один файл результата Playwright не создаётся в корне.

### Проверка
- `npm test -- --list`
- Ожидаемый результат: перечислены сценарии для desktop/mobile, offline scripts и reduced motion; приложение ещё может не пройти визуальные assertions до Фазы 2.
- `npm run start`
- Ожидаемый результат: локальная страница открывается на 127.0.0.1:4173; путь вне корня получает 404/403.

## Task 2: Добавить аудит локальных ресурсов

### Намерение
Перед перемещением 17 используемых картинок/шрифтов и удалением 144 неиспользуемых медиа-файлов получить воспроизводимый список ссылок и отсутствующих файлов. Сканер не удаляет файлы автоматически.

### Последовательность реализации
1. Создать scripts/check-local-assets.mjs на Node.js core-модулях; добавить его запуск через npm run check:assets.
2. Проверять source-файлы index.html, app.js, normal-scroll.js и hero-prize-transition.js. Из HTML брать src/href, из CSS — url(), из локальных JS-строк — относительные URL с известным расширением ресурса и скрипт, который вставляет app.js.
3. Пропускать http/https/protocol-relative/data/hash/root-relative адреса. Для относительного URL снять query и hash, URL-decode один раз, нормализовать путь от корня проекта и проверить, что результат остаётся внутри корня.
4. В обычном режиме завершаться с кодом 1 только при отсутствующей локальной ссылке; выводить источник ссылки и ожидаемый путь. С ключом --report-unused дополнительно перечислять незадействованные файлы корня с расширениями png/jpg/jpeg/svg/ttf/woff/woff2, но не удалять их.
5. Добавить режим --strict-unused для финальной проверки после переноса: кроме отсутствующих ссылок он завершается с кодом 1, если в корне остались медиа/шрифты. Ресурсы из assets/ не считаются корневыми.
6. Нормализовать ссылки относительно index.html и корня проекта, а не относительно текущего каталога процесса. Это делает результат одинаковым из корня репозитория и из CI.

### Интерфейсы и контракты
- Команды: `npm run check:assets`, `npm run check:assets -- --report-unused` и после Task 5 `npm run check:assets -- --strict-unused`.
- Выход успешной проверки: код 0 и сводка «missing=0»; --report-unused показывает список, но не удаляет файлы.
- Удаление и перенос выполняются отдельным Task 5 после просмотра отчёта. Сканер не меняет HTML, файлы или ignore-правила.
- Пути с пробелами, кириллицей, query и fragment нормализуются корректно; URL с внешней схемой не трактуются как локальные.

### Ошибки и логирование
- Некорректный URL записывается как ошибка с исходным фрагментом и именем файла.
- Verbose выводит каждую найденную ссылку и её источник; обычная команда показывает только итог и ошибки. Не печатать содержимое документа.

### Тесты
- Проверить сканер на проекте без изменения файлов: ссылки assets/fonts и локальные изображения найдены; CDN и data URI исключены; missing=0.
- После переноса повторить обычный и строгий режимы. Результаты включаются в браузерную/asset проверку Task 7.

### Критерии приёмки
- Все существующие локальные runtime-ссылки разрешаются.
- Отчёт на текущем состоянии отличает используемые ресурсы от неиспользуемых и не удаляет ничего.
- Нормализация не позволяет ссылке с traversal выйти за корень.

### Проверка
- `npm run check:assets -- --report-unused`
- Ожидаемый результат на текущем состоянии: все 17 используемых ресурсов существуют; отчёт отдельно показывает неиспользуемые root screenshots/media.
- `node --check scripts/check-local-assets.mjs`
- Ожидаемый результат: синтаксических ошибок нет.

## Риски фазы и меры
- Риск: удалённые скрипты заблокированы, но CSS/Webflow продолжает загружаться с сети. Мера: режим теста явно управляет только script-запросами; проверка полного CDN-доступа остаётся отдельной ручной проверкой.
- Риск: локальный сервер открыт за пределы проекта через traversal. Мера: нормализовать путь и проверять его относительно корня до чтения.

## Критерии завершения фазы
- Task 1 и Task 2 дают воспроизводимый запуск и отчёт без удаления текущих файлов.
- После выполнения Tasks 3–4 визуальные browser assertions становятся зелёными.
- Единственный progress ledger — checkbox-строки в index.md.
