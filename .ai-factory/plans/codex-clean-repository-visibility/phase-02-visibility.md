## Task 3: Устранить конфликт модели hero и закрепить порядок слоёв

### Намерение
В текущем CSS один и тот же hero сначала объявлен обычным блоком, а позднее становится sticky-экраном внутри сцены. Порядок слоёв и эти два режима нужно описать одной моделью, чтобы заголовок не попадал за фотографию или соседнюю секцию.

### Последовательность реализации
1. Использовать screenshot/test baseline Task 1 и computed styles при progress=0, середине перехода и его конце. Зафиксировать, какой именно элемент перекрывает #hero h1 и на каком ancestor возникает stacking context. Не повышать z-index заголовка до проверки его предков.
2. В существующем пользовательском CSS-блоке index.html оставить один режим: sticky #hero высотой 100vh в .hero-prize-transition; размеры сцены и размещение #prizes согласовать с hero-prize-transition.js. Удалить только более ранние конфликтующие правила, которые задают для этой сцены второй несовместимый режим, в том числе повторные height/min-height/transform/clip-path, если computed styles подтверждают их перекрытие.
3. Ввести в этом блоке три именованных уровня: фото=0, текст и обычный контент hero=1, соседняя панель prizes=2. Позиционировать соответствующие элементы внутри их общего контекста: #hero остаётся на уровне сцены 1; .hero-w_bg и фото ниже .hero-s; .hero-s_logo и даты над фото; декоративные элементы имеют pointer-events:none; #prizes сохраняет свой уровень 2.
4. Не поднимать дочерний z-index выше соседнего #prizes наивно: #hero — отдельный stacking context. Правило гарантирует видимость заголовка внутри #hero, а порядок двух section siblings задаётся на уровне .hero-prize-transition.
5. Сохранить логику hero-prize-transition.js: progress рассчитывается по прокрутке общей сцены; syncPhotoEdge меняет clip-path только у .hero-w_bg; в начальном состоянии progress=0 и clip-path не обрезает заголовок. Если тест показывает, что JS изменяет не тот слой/размер, исправить адресат изменения в этом файле, не перемещая текстовый слой.
6. Обновить тест: при 0 progress hit-test в центре видимого текста возвращает .hero-s_logo или его потомка, h1 и все его split spans имеют ненулевую opacity; на 390, 768 и 1440 px положение заголовка не уходит за viewport.
7. Проверить промежуточную точку: когда панель prizes начинает перекрывать hero, заголовок может исчезать только согласно progress transition; #prizes не перекрывает h1 при progress=0. В конце перехода heading «Главный приз» и сумма доступны и не обрезаны.

### Интерфейсы и контракты
- Селекторы остаются текущими: #hero, .hero-prize-transition, .hero-w_bg, .hero-s, .hero-s_logo, #prizes и CSS variable --hero-prize-progress.
- В начальном состоянии: progress≈0, фон видим, h1 видим и расположен выше фона, а #prizes не перекрывает область заголовка.
- В середине: значение progress в диапазоне 0–1, clip-path применяется к фото; никакая логика clip-path не применяется к .hero-s_logo.
- В конце: progress≈1, hero-текст завершает предусмотренный fade, заголовок главного приза видим, следующий контент не закрыт overflow родителя.
- На ширине 390 px правила из @media (max-width: 767px) не меняют порядок слоёв; на 768 px проверяется tablet layout; на 1440 px — desktop.

### Ошибки и логирование
- Нулевые размеры или отсутствующие #hero/#prizes остаются безопасным early return в hero-prize-transition.js.
- Не добавлять console.log в scroll handler. При debug=visibility разрешается одно verbose-сообщение с viewport, progress, target слоя и computed z-index; выключенный debug не меняет поведение.
- Ошибки геометрии в тесте должны печатать ancestor chain для h1 и фото, чтобы показать границы stacking context.

### Тесты
- Использовать тесты из Task 1, расширить проверку геометрии и hit-test.
- Сценарии: desktop/mobile в покое; переход на progress≈0.5; состояние progress≈1; возврат прокрутки к progress=0.
- Проверять также scroll width документа: полоса прокрутки по горизонтали не появляется из-за 100vw сцены или декоративного элемента.

### Критерии приёмки
- В самом начале страницы текст «Лучшая учебная группа 2026» читается поверх фото при всех трёх ширинах.
- z-index на детях не пытается выйти из stacking context #hero; порядок hero/prizes контролируется siblings-сценой.
- Сцена остаётся scrollable и главный приз не исчезает за hero после перехода.
- Удалённые дубли CSS не меняют нижние секции и подтверждены скриншотами перехода.

### Проверка
- `npm test -- --grep "hero"`
- Ожидаемый результат: hero-слой и прогресс проходят на всех заданных размерах.
- `npm run start` с визуальным просмотром размеров 390×844, 768×1024 и 1440×900.
- Ожидаемый результат: фото остаётся фоном, заголовок поверх него, а переход к главному призу не образует пустого или перекрытого промежутка.

## Task 4: Сделать появление текста отказоустойчивым

### Намерение
Тексты секций уже присутствуют в HTML, но app.js задаёт начальные скрытые состояния через SplitText/GSAP и рассчитывает на ScrollTrigger. При блокировке CDN, исключении во время bootstrap или пропущенном callback эти тексты не должны оставаться пустыми.

### Последовательность реализации
1. Встроенный watchdog index.html сделать единым источником fail-open поведения. Состояния диагностической переменной: pending, ready и fallback. Начальное состояние не скрывает содержимое.
2. Перед подключением динамического app.js проверить обязательные globals, которыми он пользуется на top level: gsap, ScrollTrigger, SplitText и CustomEase; отдельно проверить Lenis/Barba до функций, которые их вызывают. Если обязательная зависимость отсутствует, не загружать app.js, выставить fallback и оставить контент доступным.
3. В app.js, в initScrollElementsReveal, создавать reveal-анимации только когда зависимости существуют и prefers-reduced-motion не включён. Устанавливать начальную opacity/transform только для элементов, для которых успешно создан ScrollTrigger callback; не обнулять все секции заранее.
4. После успешной регистрации текстовых триггеров вызвать существующий callback window.__lugRevealReady() из inline-bootstrap. Callback переводит состояние в ready и отменяет общий watchdog. Инициализация должна быть идемпотентной при повторном initScripts().
5. Если bootstrap не сообщил ready за 2200 ms, поймал исключение локального app.js или отсутствует обязательная библиотека, вызвать window.__lugRevealAll(reason). Функция снимает opacity/visibility/clip-path/transform только у [data-scroll-reveal], [data-prevent-flicker] и добавленных SplitText-потомков; текстовое содержимое и порядок DOM не меняются.
6. Для каждого pending reveal добавить конечный failsafe не длиннее длительности анимации плюс максимальной задержки и 500 ms. Если callback не завершил reveal, принудительно показать его target и записать единый reason code; таймеры освобождать при reveal и при fallback.
7. При prefers-reduced-motion не создавать скрытые начальные состояния, сразу показывать все reveal targets и не запускать hero scroll-анимацию. При повторном resize не скрывать уже видимый контент.
8. Добавить обработчик window error для ошибок именно локального app.js до срабатывания ready. Он вызывает единый fallback; сторонние expected сетевые ошибки не должны повторно запускать fallback.
9. Добавить браузерные assertions: заблокировать удалённые scripts и проверить видимость всех 9 секций после fallback; отдельно оставить scripts включёнными и пройти прокруткой от hero до CTA, проверяя каждую секцию после появления.

### Интерфейсы и контракты
- window.__lugRevealState принимает только pending, ready, fallback; window.__lugRevealReady() и window.__lugRevealAll(reason) идемпотентны.
- reason ограничен перечисленными строковыми кодами: missing-dependency, app-script-error, setup-timeout, reveal-timeout, reduced-motion. Не включать URL, пользовательский текст, email, телефон или содержимое формы.
- После fallback все текстовые targets имеют visibility=visible, opacity=1, transform:none, clip-path:none; CSS background и clip-path фото не сбрасываются.
- Для штатного режима app.js сохраняет анимации текущих атрибутов data-scroll-reveal, но текст обязан появиться после одного scroll-entry. Секции вне viewport не остаются скрытыми при отключённых scripts.
- При повторном Barba/page setup вызов готовности не создаёт второй watchdog и не скрывает текст, который уже видим.

### Ошибки и логирование
- Отсутствующая CDN-библиотека — нормальный fallback, не фатальная ошибка контента. Нужный для оформления внешний stylesheet не подменяется этим механизмом.
- Ошибка setup вызывает fallback немедленно; watchdog остаётся последней защитой, но не замещает явный callback готовности.
- В verbose debug=visibility записывать один DEBUG с состоянием и reason; без debug — одна WARN при fallback и никаких сообщений на каждый scroll/элемент. Не логировать поля формы.

### Тесты
- Заблокированные удалённые scripts: после fallback все заголовки и основной текст видимы, pageerror от локального кода отсутствует, ни один split span не остаётся с нулевой opacity.
- Штатный режим: все секции открываются при последовательном scroll; H1 видим до начала hero transition.
- Reduced motion: все секции видимы без ожидания reveal.
- Имитированное исключение локального app.js: fallback снимает скрытое состояние и вызывается только один раз.

### Критерии приёмки
- Отказ CDN или анимационного callback не оставляет секцию визуально пустой.
- Все девять текущих секций содержат те же исходные тексты и видны при прокрутке страницы.
- Принудительный fallback не обрезает campus photo и не сбрасывает progress сцены.
- В штатном режиме reveal-анимации продолжают работать; в reduced-motion они пропускаются.

### Проверка
- `npm test -- --grep "visibility"`
- Ожидаемый результат: offline scripts, штатный scroll и reduced-motion проходят.
- `node --check app.js`
- Ожидаемый результат: синтаксис app.js корректен.

## Риски фазы и меры
- Риск: отключение сторонней CSS ломает исходный дизайн. Мера: автоматический тест отключает только remote scripts; полноэкранный стиль CDN остаётся отдельной внешней зависимостью и не подменяется.
- Риск: лишний failsafe убирает запланированную анимацию. Мера: таймер привязан к конкретному target и срабатывает только если его reveal не завершился.
- Риск: приложение импортирует Barba/GSAP глобально в нескольких местах. Мера: проверить все globals из index.html до подключения app.js и покрыть blocked-script сценарием.
