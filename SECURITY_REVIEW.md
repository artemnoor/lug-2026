# Security review — ЛУГ 2026

Дата проверки: 29 августа 2026 года.

## Итог

Проект имеет хороший базовый уровень защиты для локальной разработки и
контролируемого staging. Регистрация теперь использует email вместо телефона:
код генерируется криптографически, в хранилище попадает только HMAC-код и хэш
пароля, а сессия создаётся только после подтверждения адреса.

Текущий staging уже использует PostgreSQL, Redis, private S3, обязательный
ClamAV scanner и SMTP Mail.ru по SSL/465. Публичный production-запуск пока
нельзя считать завершённым без TLS/reverse proxy, закрытого origin,
внешнего управления секретами, резервного копирования и контроля
доставляемости SMTP. Mailpit, поднятый локально, предназначен только для
тестов и не отправляет письма наружу.

## Что проверено

- `npm run check` — синтаксис JS/Python и quality-проверки проходят.
- `ruff check apps/api/app` — ошибок нет.
- `npm run test:smoke` — проходят CSRF, RBAC, BOLA для файлов, mass assignment,
  rate limits, удалённый chat API и полный email verification flow.
- `npm run test:smtp-local` — SMTP-письмо действительно принято Mailpit,
  проверены получатель, тема и HTML-содержимое.
- `pip-audit -r apps/api/requirements.txt --progress-spinner off` — известных
  уязвимостей в зависимостях API не найдено.
- `npm audit --omit=dev` — 0 уязвимостей.
- Production-конфигурация без SMTP или без HMAC-secret завершается ошибкой до
  запуска, а режим `log` в production запрещён.

Strix в окружении не установлен, а публичные правила Semgrep не загрузились
из-за недоступного/неподходящего registry-конфига. Поэтому это не заявление о
полном внешнем penetration test; авторизационные проверки выполнены локальным
сквозным тестом с несколькими независимыми клиентами.

## Контроли приложения

### Аутентификация и подтверждение email

- Email нормализуется и валидируется; login использует email и пароль.
- Код состоит из шести цифр и создаётся через `secrets.randbelow`.
- В persistent store не записываются ни исходный код, ни исходный пароль.
- Код хранится как HMAC-SHA-256 с отдельным `LUG_EMAIL_VERIFICATION_SECRET`.
- Есть TTL, cooldown повторной отправки, лимит неверных попыток и IP rate limit.
- До подтверждения email нет пользователя и нет сессии.
- Новые пароли хранятся через `Argon2id`, старые `scrypt`-хеши поддерживаются для бесшовной миграции; токены сессий — только в виде SHA-256-хэшей.
- Восстановление пароля использует отдельное HMAC-состояние с TTL, cooldown,
  лимитом попыток и rate limit; после успеха все сессии пользователя отзываются.
- Смена bootstrap email/пароля отзывает старые сессии администратора.
- Login использует единое сообщение ошибки для неизвестного email и неверного
  пароля.

### Авторизация и данные

- Админские endpoints защищены ролью; участник не может вызвать admin API.
- Файлы не раздаются публично: проверяется владелец, команда или администратор.
- Входные модели запрещают лишние поля (`extra="forbid"`), что закрывает
  проверенный mass-assignment сценарий.
- Есть лимиты тела запроса, файлов, количества и суммарного размера загрузок, а также отдельный IP/user rate limit для upload endpoints.
- В production загрузки требуют настроенного AV scanner; при сбое проверка
  закрывается fail-closed.
- При замене фото личного кабинета новый объект проходит тот же набор проверок,
  старый объект удаляется только после успешного сохранения нового, а администраторское
  уведомление не содержит сам файл и не открывает публичный доступ к нему.
- Email-копии уведомлений отправляются только подтверждённым адресатам; массовая
  отправка ограничена конкурентностью, а ошибки отдельных ящиков не раскрывают
  адреса другим получателям.
- Chat API и старые chat-уведомления удалены из runtime и нормализуются из
  legacy JSON при следующей записи.

### HTTP и эксплуатация

- Изменяющие запросы требуют same-origin CSRF cookie/header.
- Production включает secure cookies; заданы security headers, no-store для
  чувствительных ответов и private no-store для файлов.
- Readiness и metrics закрыты operations token или loopback-доступом.
- Доверие к `X-Forwarded-For` включается только для явно перечисленных proxy IP.
- PostgreSQL хранит сущности отдельными строками с индексами; audit log вынесен в
  отдельную таблицу с retention 730 дней, а метрики используют bounded histograms.
- S3 uploads хранятся в private bucket, ключи не содержат пользовательских имён,
  а доступ выдаётся только после BOLA-проверки через короткий presigned URL.
- Nginx-шаблон проксирует трафик через Node gateway и не открывает FastAPI
  напрямую.

## Что нельзя считать закрытым до production

1. Перенести SMTP-пароль Mail.ru и остальные production-секреты в secret manager;
   отдельно подтвердить доставку кодов, восстановления пароля и уведомлений.
2. Поставить TLS и edge WAF/CDN, закрыть origin-порты firewall и включить
   администраторскую MFA/SSO.
3. Задать случайный secret manager-backed
   `LUG_EMAIL_VERIFICATION_SECRET` длиной не менее 32 символов.
4. Проверить backup/restore PostgreSQL и lifecycle policy object storage; local
   storage в production конфигурация не допускается.

Секреты, реальные SMTP-пароли, `data/lug.json` и пользовательские uploads не
должны попадать в репозиторий или архив проекта.
